# AGENTS.md

High-signal guidance for Codex, OpenCode, GitHub Copilot, and other supported coding-agent sessions working in this repo. Read alongside `DEVELOPMENT.md` and `.specify/memory/constitution.md`.

## Repo shape

Two-stack monorepo, currently mid-implementation (feature 001 — auth/roles/profile — is in progress):

- `backend/` — Go 1.22 service, module `halaqaty/backend`. Entry point `backend/cmd/api/`. Domain packages under `backend/internal/` (currently `auth`, `profile`, `rbac`, `middleware`, `platform`). DB migrations in `backend/migrations/` (golang-migrate, paired `*.up.sql` / `*.down.sql`).
- `mobile/` — Flutter app, package `halaqaty_mobile`. Riverpod 2.x + go_router + dio. Feature-first layout under `mobile/lib/features/`, with `core/` and `main.dart`.
- `specs/` — **generated by Spec-Kit, do not edit by hand.** Each feature gets `specs/NNN-name/` with `spec.md`, `plan.md`, `data-model.md`, `contracts/`, `tasks.md`.
- `docs/` — strategy/architecture/ADRs. `docs/contracts/openapi.yaml` is the REST source of truth; `docs/contracts/ws_events.md` the WebSocket catalog.
- Root `Makefile` delegates to `backend/Makefile` and `mobile/Makefile`. Cross-cutting targets (Docker Compose, gitleaks, Spectral) live only at root.

## Workflow — Spec-Kit is mandatory

All features follow the 7-phase Spec-Kit pipeline (`/speckit.specify → clarify → checklist → plan → tasks → analyze → implement`). No ad-hoc feature code. Before writing code for a feature:

1. Read `.specify/memory/constitution.md` (governing document) and `DEVELOPMENT.md`.
2. Confirm the feature is `🟡 Approved` in `docs/management/product/FEATURES.md` and decisions are frozen in `docs/management/product/MVP_DECISION_REGISTER.md`.
3. Verify against `specs/NNN-feature/plan.md` — DB schema must match `docs/engineering/architecture/ARCHITECTURE.md`; no new tables/columns without an ADR.

`DO NOT GUESS` — when requirements are ambiguous, surface clarifying questions rather than inventing fields or endpoints.

Branch naming: `NNN-feature-name` (Spec-Kit creates these). PR title format enforced by CI: `HLQ-NNN: feature name`. Commits follow Conventional Commits.

## Agents & Skills

This project uses a multi-agent workflow with specialized agents and quality-guard skills. OpenCode definitions live under `.opencode/agents/` and `.opencode/skills/`; GitHub Copilot definitions live under `.github/agents/` and `.github/skills/`. In Codex, use a callable role agent when available; otherwise read the matching `.github/agents/<role>.agent.md` as the role instructions. The Team Leader (`team-leader`) is the default coordinator.

### Agentic Workflow Harness

Spec-Kit, Superpowers, role-based agents, Ponytail, and project quality skills have distinct responsibilities. The authoritative integration and token-efficiency policy is:

`docs/engineering/collaboration/AGENT_WORKFLOW_HARNESS.md`

Apply these rules on every feature task:

1. **Spec-Kit owns scope and artifacts** — `specify → clarify → checklist → plan → tasks → analyze → implement` remains the only feature lifecycle.
2. **Superpowers owns implementation discipline** — use its TDD, debugging, focused review, and verification skills during implementation; do not recreate approved Spec-Kit specifications or plans with Superpowers.
3. **Role agents own domain work** — dispatch only the smallest set of agents needed for the current phase and task. Collaboration does not mean dispatching every agent.
4. **Ponytail owns restraint** — prefer the smallest correct implementation inside approved Spec-Kit scope; never use Ponytail to skip required validation, security, accessibility, contracts, tests, or acceptance criteria.
5. **Project guards remain quality gates** — `$clean-code-guard`, `$test-guard`, and `$docs-guard` audit their respective changed artifacts without duplicating the Tech Lead review.
6. **Minimize context** — pass task IDs and file paths instead of pasting documents; keep one implementer and one reviewer per coherent batch by default.

If instructions conflict, follow the precedence and escalation rules in the harness. Never silently choose between contradictory approved artifacts.

### Spec-Kit Workflow

All features follow the Spec-Kit pipeline. Use the corresponding `/speckit.*` commands — each routes to its dedicated agent:

| Command | Purpose |
|---|---|
| `/speckit.specify` | Create/update feature specification |
| `/speckit.clarify` | Resolve ambiguities in the spec |
| `/speckit.checklist` | Validate spec quality and completeness |
| `/speckit.plan` | Generate implementation plan and design artifacts |
| `/speckit.tasks` | Break plan into actionable tasks |
| `/speckit.analyze` | Cross-artifact consistency check (spec ↔ plan ↔ tasks) |
| `/speckit.implement` | Execute tasks and produce code |

## Common developer commands

Run from repo root unless noted:

```
make dev                 # start infra (PostgreSQL, MinIO, LiveKit) via docker compose + show status
make migrate-up          # apply pending migrations (needs DATABASE_URL)
make migrate-fresh       # ⚠️ drop schema + re-run all migrations (destroys data)
make migrate-create NAME=create_foo   # new migration pair
make test                # Go unit (-short) + Flutter unit/widget
make test-integration    # Go integration tests (needs DATABASE_URL + running Postgres)
make lint                # golangci-lint + flutter analyze + spectral + gitleaks
make api-lint            # spectral lint docs/contracts/openapi.yaml (config: .spectral.yaml)
make secrets             # gitleaks detect across repo
make build               # Go binary (backend/bin/api) + Flutter debug APK
go run ./cmd/api         # run backend (from backend/)
flutter run              # run mobile app (from mobile/, after `flutter pub get`)
```

`DATABASE_URL` must be exported for any `migrate-*` or integration test target, e.g. `postgres://user:pass@localhost:5432/halaqaty?sslmode=disable`. The Makefiles fail fast if it's unset.

### Focused / single-package tests

```
# Backend: one package
cd backend && go test -short ./internal/auth
# Backend: feature-001 scoped targets (unit / contract / integration)
cd backend && make test-feature-001-unit
cd backend && make test-feature-001-contract
cd backend && make test-feature-001-integration   # needs DATABASE_URL
# Backend: run a single Go test by name
cd backend && go test -run TestName ./internal/auth

# Mobile: one widget test dir or single file
cd mobile && flutter test test/widget/auth
cd mobile && flutter test test/widget/auth/some_test.dart
```

Contract tests run with `-tags=contract` and a `-run` regex filter (`Auth|Profile|CircleAssignRole|ResponseSafety`); integration tests use `-tags=integration` with `AuthFlow|ProfileFlow|CircleRoleAccess|RateLimitPolicy|PasswordStorageSafety`. Mirror these filters when adding features.

## Quality gates (all must be green before PR)

| Gate | Command |
|---|---|
| Go unit | `go test -short ./...` (run in `backend/`) |
| Go integration | `go test -tags=integration ./...` (needs `DATABASE_URL`) |
| Go lint | `golangci-lint run ./...` (v1.64.x, zero violations) |
| Go fmt | `gofmt -l .` (empty output) |
| Flutter test | `flutter test test` (in `mobile/`) |
| Flutter analyze | `flutter analyze` (zero issues) |
| Dart fmt | `dart format --set-exit-if-changed .` (no diff) |
| OpenAPI lint | `make api-lint` (Spectral OAS rules) |
| Secret scan | `make secrets` (gitleaks) |
| Tech Lead review | Hard gate via PR (mandatory manual deep-review by Karim for auth, RBAC, deletion paths, Firebase Auth, MinIO/upload) |

CI runs the lint workflow (`lint.yml`) and unit/integration tests (`tests-unit-integration.yml`) on PRs and pushes to `main`.

## Backend code conventions (enforced)

From `.github/copilot-instructions.md` — these are not obvious from filenames:

- Reuse centralized HTTP/API constants from `backend/internal/platform/httpconst/` (headers, auth scheme, content types, shared error messages). Do **not** inline these literals in handlers or middleware.
- Keep SQL out of repository method bodies. Define statements in package-level `*_queries.go` files and reference them from repository methods.
- Centralize HTTP route patterns in `backend/cmd/api/routes.go`; reference them from router wiring. Avoid inline `"METHOD /path"` literals in handlers.
- Wrap errors with `fmt.Errorf("operation: %w", err)`; never discard errors silently. All exported Go functions need a doc comment.

## Mobile code conventions

- Riverpod for all state management — no `setState` in feature code (only in isolated leaf widgets).
- `async` functions must handle errors at the call site or bubble them to the nearest error boundary provider.
- Arabic-first / RTL-aware UI — verify layouts in both directions.

## Contracts & docs

- Changing REST surface → update `docs/contracts/openapi.yaml` and re-run `make api-lint`. Spectral config in `.spectral.yaml` extends the official OAS ruleset (unique `operationId`, resolvable `$ref`, 2xx on each operation, etc.).
- Changing WebSocket surface → update `docs/contracts/ws_events.md`.
- Per-feature contract overrides live in `specs/NNN-feature/contracts/` (generated).
- Technical docs (ARCHITECTURE, ADRs) stay English; only business/product docs are mirrored to Arabic (see `docs/management/arabic/SYNC_GUIDE.md`).

## Gotchas

- `go.mod` lives in `backend/`, `pubspec.yaml` in `mobile/` — there is no root `go.mod`/`pubspec.yaml`. Run Go/Flutter commands from those subdirs (or use the root Makefile, which sets `working-directory` correctly). The unit/integration CI workflow detects stacks by checking for `go.mod`/`pubspec.yaml` **at repo root**, so its Go/Flutter jobs may be skipped — always validate with `make test` locally before relying on green CI.
- `specs/NNN-feature/` artifacts are generated by Spec-Kit. Editing them manually will be overwritten on the next `/speckit.plan`/`/speckit.tasks` run.
- New tables/columns require an ADR under `docs/engineering/architecture/adr/` and must match `ARCHITECTURE.md`.
- Security-sensitive code (auth handlers, JWT validation, RBAC, deletion paths, Firebase Auth integration, MinIO upload controls) gets a mandatory manual deep-review by Karim — don't merge until reviewed.

# F-006 Data Model

**Status:** Approved by ADR-026 and reflected in architecture; paired migration `000020_schedule_calendar_attendance` is implemented. All instants are UTC `TIMESTAMPTZ`; all recurring civil dates/times use the stored IANA zone. Existing F-005 tables are extended by relationship, not redefined.

## State and write boundaries

- **Virtual recurrence**: A calendar occurrence exists by computation even without a `sessions` row. Its public key is the schedule UUID plus original local date. An edited/cancelled exception keeps that key.
- **Materialized start**: Refactor the F-005 repository transaction body for reuse. In one transaction, lock the parent schedule, recheck revision/exception/details cancellation, insert or reuse one `sessions` row and `planned_session_details`, then run the existing F-005 start/media/admission body and snapshot the actual-start roster. There is no commit between materialization and activation. Recurring cancellation and series edits take the same parent lock before checking/updating exception and detail; a virtual cancellation does not require a session row. F-005's media adapter remains inside its serialized transaction with existing rollback/reconciliation behavior. One-off start/cancel locks the session and rechecks details.
- **One-off**: Create F-005 `sessions` with non-null `scheduled_at` plus `planned_session_details` immediately. Cancel by setting only `planned_session_details.cancelled_at` while still unstarted. F-005 discovery excludes such cancelled planned rows, while the F-006 calendar retains them. An ad-hoc F-005 row has null `scheduled_at` and no details row.
- **Series edit/stop**: CAS `schedules.current_version`, append a revision effective on the requested local date, and invalidate affected unstarted exceptions and planned materializations. Earlier revisions continue to reproduce past virtual occurrences; started/completed rows and attendance remain unchanged. If a materialized unstarted occurrence has become active concurrently, the operation reports conflict/reloads rather than changing history.
- **Attendance**: F-005 activation snapshots current active student membership. For a student absent from that snapshot, the join/presence transaction locks and rechecks their current `circle_members` student row (`FOR KEY SHARE`) and upserts `session_attendance` with `roster_source=later_participant` before committing presence; concurrent membership deletion waits, and later deletion cannot erase roster eligibility. F-005 end (including automatic end/recovery) triggers idempotent finalization using roster rows and presence, without reconstructing eligibility from current membership. `first_joined_at` is read-only. Threshold is inclusive at actual start + 10 minutes. Corrections are append-only and survive recomputation.
- **Archive/revocation**: Historical rows are retained. Every read uses current `circle_members` and circle state; archive permits reads but denies writes. Revocation removes access, not data. No automatic student access from old attendance rows.

## Migration sequence and rollback

1. ADR-026 is accepted; `ARCHITECTURE.md` and canonical REST contract are synchronized to this model.
2. Paired migration `backend/migrations/000020_schedule_calendar_attendance.{up,down}.sql` adds the profile timezone column and new tables/constraints/indexes without altering F-005 enums or dropping existing columns. It backfills existing profile rows to `UTC`. Fresh up/down and upgrade from an existing profile were verified in the recorded Phase 7 gates in [quickstart.md](quickstart.md); no old schedule rows existed to backfill. Production rollback retains additive data until deliberate migration, especially attendance history.
3. Deploy compatible readers before exposing F-006 writes. Down migration is safe only while no F-006 data must be retained; for production rollback, disable F-006 routes and roll back code while leaving additive tables, then migrate data deliberately. Never drop attendance history as an automatic incident response.

## Query boundaries

- Calendar uses a requested year/month in the viewer's stored profile zone. For each relevant rule, compute the earliest start that could intersect the month as `month_start - duration_minutes`, jump to the first recurrence candidate at or after that lower bound, then generate only candidates through month end; also include persisted one-offs, moved exceptions and started/completed/cancelled history. The approved 31-day planned-duration bound caps lookback and result work without a creation-date horizon. The API supports pagination or chunked month reads; it never fetches all future dates.
- Overlap comparisons are half-open `[start,end)`, so touching endpoints do not collide. Cross-circle warnings are limited to commitments the acting manager can currently read. Student warning calculation uses only that student's eligible calendar.
